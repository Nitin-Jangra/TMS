     7→# 1. PROJECT OVERVIEW
     8→
     9→Build a complete, production-quality, standalone Complaint & Ticket Management System for FitClass Gym.
    10→
    11→The application will allow FitClass customers to register complaints through a public complaint portal, receive a unique ticket number, track their complaint status, and reopen resolved complaints within a configurable period.
    12→
    13→The system will automatically distribute complaints among eligible support employees of the respective branch using an equal, branch-wise round-robin assignment algorithm.
    14→
    15→Central support, branch managers and support employees will manage complaints through dedicated dashboards with role-based permissions.
    16→
    17→**IMPORTANT DEVELOPMENT DECISION:**
    18→
    19→For the initial development and testing phase, use a completely separate Supabase development project containing dummy data.
    20→
    21→Do not connect to the actual FitClass production database, actual CRM, or real customer records.
    22→
    23→Build the architecture so that the development Supabase project can later be replaced with a fresh production Supabase project through environment configuration and database migrations without rewriting business logic.
    24→
    25→Do not build only a frontend prototype. Implement the frontend, backend, database, authentication, authorization, APIs, notifications, assignment engine, background jobs, security controls and automated tests.

   272→# 7. TICKET STATUS MANAGEMENT
   273→
   274→Implement exactly these five primary statuses:
   275→
   276→```text
   277→NEW_COMPLAINT
   278→IN_PROGRESS
   279→ON_HOLD
   280→RESOLVED
   281→CLOSED
   282→```
   283→
   284→### Status definitions
   285→
   286→**NEW_COMPLAINT**
   287→- Ticket has been registered.
   288→- Ticket has been assigned or is awaiting assignment.
   289→- Initial status remains New Complaint until support begins handling it.
   290→
   291→**IN_PROGRESS**
   292→- Assigned support person is actively investigating the complaint.
   293→
   294→**ON_HOLD**
   295→- Support person is waiting for information, action or resolution.
   296→- A reason must be provided.
   297→- Support person can resume the ticket.
   298→
   299→**RESOLVED**
   300→- Support person has provided a solution.
   301→- Resolution message is mandatory.
   302→- Customer is notified.
   303→- Reopening countdown starts.
   304→
   305→**CLOSED**
   306→- Ticket is automatically closed after the configured reopening window expires.
   307→- Closed tickets become permanently read-only.
   308→
   309→### Allowed status transitions
   310→
   311→```text
   312→NEW_COMPLAINT → IN_PROGRESS
   313→
   314→IN_PROGRESS → ON_HOLD
   315→IN_PROGRESS → RESOLVED
   316→
   317→ON_HOLD → IN_PROGRESS
   318→ON_HOLD → RESOLVED
   319→
   320→RESOLVED → IN_PROGRESS (Customer Reopening)
   321→
   322→RESOLVED → CLOSED (Automatic System Closure)
   323→```
   324→
   325→Reject every other transition.
   326→
   327→### Important closed-ticket restriction
   328→
   329→Once a ticket becomes CLOSED:
   330→
   331→- No support employee can update it.
   332→- No branch manager can update it.
   333→- No central support agent can update it.
   334→- No Root Admin can modify its status.
   335→- No API endpoint can reopen it.
   336→- No normal application operation can modify its content or assignment.
   337→
   338→Closed tickets must remain accessible as read-only historical records.
   339→
   340→Implement this restriction at the database level, not just in frontend controls.

   344→# 8. BRANCH-WISE ROUND-ROBIN ASSIGNMENT ENGINE
   345→
   346→This is a core business requirement.
   347→
   348→Every branch must have an independent assignment queue.
   349→
   350→### Example
   351→
   352→Sector 48:
   353→- Employee A.
   354→- Employee B.
   355→- Employee C.
   356→- Employee D.
   357→
   358→Assignment:
   359→
   360→```text
   361→Ticket 001 → Employee A
   362→Ticket 002 → Employee B
   363→Ticket 003 → Employee C
   364→Ticket 004 → Employee D
   365→Ticket 005 → Employee A
   366→Ticket 006 → Employee B
   367→```
   368→
   369→### Assignment rules
   370→
   371→1. Every newly submitted complaint enters the assignment engine.
   372→2. The engine identifies the selected branch.
   373→3. Fetch active employees from the dummy employee master.
   374→4. Identify employees eligible for complaint assignment.
   375→5. Assign the ticket to the next eligible employee.
   376→6. Update the persistent branch assignment cursor.
   377→7. Record the assignment in the database.
   378→8. Send an assignment notification.
   379→9. Repeat the cycle for the next complaint.
   380→
   381→### Equal distribution rules
   382→
   383→- Use FIFO round-robin.
   384→- Each eligible employee receives an equal number of tickets over a complete assignment cycle.
   385→- Maintain a separate cursor for each branch.
   386→- Never mix assignment queues between branches.
   387→- Assignment must be concurrency-safe.
   388→- Maintain complete assignment history.
   389→- Reopened complaints should retain their original assignee if still eligible.
   390→- If the original assignee is unavailable, assign through the branch queue.
   391→
   392→### Employee availability
   393→
   394→An employee is eligible only if:
   395→- Active in the employee master.
   396→- Has the correct support role.
   397→- Belongs to the relevant branch.
   398→- Complaint assignment availability is enabled.
   399→
   400→If unavailable, skip that employee.
   401→
   402→Do not use workload-based distribution or weighted round-robin. The finalized requirement is equal distribution.
   403→
   404→### No eligible employee
   405→
   406→If no eligible employee is available:
   407→- Create the complaint normally.
   408→- Preserve NEW_COMPLAINT status.
   409→- Put it into the unassigned queue.
   410→- Notify branch manager and central support.
   411→- Retry assignment when an eligible employee becomes available.
   412→
   413→Implement assignment using PostgreSQL transactions and row-level locking.

   474→# 10. CUSTOMER TICKET REOPENING
   475→
   476→A customer must be able to reopen a resolved ticket using the same ticket ID.
   477→
   478→### Reopening requirements
   479→
   480→- Reopening is permitted only when the ticket is RESOLVED.
   481→- The reopening deadline must not have expired.
   482→- Verify the original registered mobile number.
   483→- Require a reopening reason.
   484→- Keep the original ticket ID.
   485→- Do not create a duplicate complaint.
   486→- Change the status to IN_PROGRESS.
   487→- Record the reopening event.
   488→- Preserve all previous status history.
   489→- Notify the customer and assigned support employee.
   490→
   491→### Reopening deadline
   492→
   493→The reopening window must be configurable by Root Admin.
   494→
   495→Do not hardcode 24, 48 or 72 hours.
   496→
   497→Store the calculated `auto_close_at` timestamp on each ticket when it becomes RESOLVED.
   498→
   499→Existing resolved tickets must retain their calculated deadlines when the global configuration changes, unless an authorized Root Admin explicitly applies a new policy.
   500→
   501→### Reopening after closure
   502→
   503→Once CLOSED, a ticket cannot be reopened by anyone.
   504→
   505→Display:
   506→
   507→"Your ticket has already been closed and can no longer be reopened. Please submit a new complaint if you need further assistance."

   511→# 11. AUTOMATIC TICKET CLOSURE
   512→
   513→Build a durable background closure engine.
   514→
   515→When a ticket becomes RESOLVED:
   516→
   517→1. Record resolution timestamp.
   518→2. Fetch the active closure policy.
   519→3. Calculate the reopening deadline.
   520→4. Store the deadline in the ticket record.
   521→5. Send customer resolution email.
   522→6. Schedule automatic closure.
   523→
   524→When the deadline expires:
   525→
   526→1. Fetch the ticket.
   527→2. Confirm that its status is still RESOLVED.
   528→3. Confirm that the current time has reached its stored deadline.
   529→4. Lock the ticket row.
   530→5. Change the status to CLOSED.
   531→6. Record status history.
   532→7. Record audit event.
   533→8. Send closure notification.
   534→9. Mark the closure job completed.
   535→
   536→The closure worker must be idempotent.
   537→
   538→If the customer reopens the ticket before closure, cancel or invalidate the pending closure job.
   539→
   540→Protect against simultaneous reopening and automatic closure using database transactions and row-level locking.
   541→
   542→Do not rely on JavaScript timers or in-memory scheduling.

   668→# 14. COMPLETE SECURITY REQUIREMENTS
   669→
   670→Treat security as a core architectural requirement.
   671→
   672→Implement security at the frontend, backend, API, database and infrastructure layers.
   673→
   674→## A. Authentication security
   675→
   676→- Use Supabase Auth for dummy development staff accounts.
   677→- Use secure session handling.
   678→- Verify JWT signatures, issuer, audience and expiry on the backend.
   679→- Never trust frontend-supplied role or employee IDs.
   680→- Implement secure password policies.
   681→- Add login rate limiting.
   682→- Add account lockout or progressive throttling after repeated failures.
   683→- Support secure password reset.
   684→- Provide logout and session revocation.
   685→- Use MFA for Root Admin and privileged production accounts.
   686→- Keep customer public access separate from employee authentication.
   687→
   688→Production staff authentication should be integrated with FitClass CRM through a replaceable authentication adapter.
   689→
   690→## B. Authorization security
   691→
   692→Implement RBAC with resource-level checks.
   693→
   694→Every protected request must validate:
   695→- User identity.
   696→- Tenant membership.
   697→- Role.
   698→- Permission.
   699→- Branch access.
   700→- Ticket ownership or assignment.
   701→- Current ticket status.
   702→
   703→Use deny-by-default authorization.
   704→
   705→Do not depend on frontend visibility controls.
   706→
   707→An employee must not access a ticket simply by changing the ticket ID in the API URL.
   708→
   709→## C. PostgreSQL Row Level Security
   710→
   711→Enable RLS on all sensitive tables.
   712→
   713→Implement policies for:
   714→- Complaint tickets.
   715→- Ticket assignments.
   716→- Ticket messages.
   717→- Ticket attachments.
   718→- Ticket history.
   719→- Employee availability.
   720→- Configuration records.
   721→- Notification records.
   722→- Audit logs.
   723→
   724→Public anonymous users must not have direct database access to complaint records.
   725→
   726→Use a secure backend service for public complaint submission and tracking.
   727→
   728→Never expose the service-role key in frontend code.
   729→
   730→The database must enforce tenant and branch restrictions wherever feasible.
   731→
   732→## D. API security
   733→
   734→Implement:
   735→- HTTPS-only production traffic.
   736→- Strict CORS allowlist.
   737→- Request body size limits.
   738→- Input validation.
   739→- Output filtering.
   740→- API rate limiting.
   741→- Secure HTTP headers.
   742→- SQL injection prevention.
   743→- XSS prevention.
   744→- CSRF protection where cookie-based sessions are used.
   745→- Request timeouts.
   746→- Secure error handling.
   747→- API versioning.
   748→- Idempotency keys.
   749→- Abuse monitoring.
   750→
   751→Never return stack traces, database errors, credentials or internal implementation details to clients.
   752→
   753→## E. Customer tracking security
   754→
   755→Ticket ID + mobile number must both match.
   756→
   757→Additional controls:
   758→- Normalize mobile numbers.
   759→- Rate-limit failed tracking attempts.
   760→- Use generic invalid-ticket responses.
   761→- Apply progressive delays or temporary throttling.
   762→- Avoid logging full phone numbers.
   763→- Avoid placing phone numbers in URL query parameters.
   764→- Return only minimum required customer data.
   765→- Keep internal messages private.
   766→
   767→Plan an optional OTP verification upgrade.
   768→
   769→## F. File upload security
   770→
   771→- Private storage buckets.
   772→- Allowlisted MIME types.
   773→- File signature verification.
