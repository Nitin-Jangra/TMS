## Complete Application Development, Security Architecture & Supabase Dummy Database

# 1. PROJECT OVERVIEW

Build a complete, production-quality, standalone Complaint & Ticket Management System for FitClass Gym.

The application will allow FitClass customers to register complaints through a public complaint portal, receive a unique ticket number, track their complaint status, and reopen resolved complaints within a configurable period.

The system will automatically distribute complaints among eligible support employees of the respective branch using an equal, branch-wise round-robin assignment algorithm.

Central support, branch managers and support employees will manage complaints through dedicated dashboards with role-based permissions.

**IMPORTANT DEVELOPMENT DECISION:**

For the initial development and testing phase, use a completely separate Supabase development project containing dummy data.

Do not connect to the actual FitClass production database, actual CRM, or real customer records.

Build the architecture so that the development Supabase project can later be replaced with a fresh production Supabase project through environment configuration and database migrations without rewriting business logic.

Do not build only a frontend prototype. Implement the frontend, backend, database, authentication, authorization, APIs, notifications, assignment engine, background jobs, security controls and automated tests.

# 7. TICKET STATUS MANAGEMENT

Implement exactly these five primary statuses:

```text
NEW_COMPLAINT
IN_PROGRESS
ON_HOLD
RESOLVED
CLOSED
```

### Status definitions

**NEW_COMPLAINT**
- Ticket has been registered.
- Ticket has been assigned or is awaiting assignment.
- Initial status remains New Complaint until support begins handling it.

**IN_PROGRESS**
- Assigned support person is actively investigating the complaint.

**ON_HOLD**
- Support person is waiting for information, action or resolution.
- A reason must be provided.
- Support person can resume the ticket.

**RESOLVED**
- Support person has provided a solution.
- Resolution message is mandatory.
- Customer is notified.
- Reopening countdown starts.

**CLOSED**
- Ticket is automatically closed after the configured reopening window expires.
- Closed tickets become permanently read-only.

### Allowed status transitions

```text
NEW_COMPLAINT → IN_PROGRESS

IN_PROGRESS → ON_HOLD
IN_PROGRESS → RESOLVED

ON_HOLD → IN_PROGRESS
ON_HOLD → RESOLVED

RESOLVED → IN_PROGRESS (Customer Reopening)

RESOLVED → CLOSED (Automatic System Closure)
```

Reject every other transition.

### Important closed-ticket restriction

Once a ticket becomes CLOSED:

- No support employee can update it.
- No branch manager can update it.
- No central support agent can update it.
- No Root Admin can modify its status.
- No API endpoint can reopen it.
- No normal application operation can modify its content or assignment.

Closed tickets must remain accessible as read-only historical records.

Implement this restriction at the database level, not just in frontend controls.

# 8. BRANCH-WISE ROUND-ROBIN ASSIGNMENT ENGINE

This is a core business requirement.

Every branch must have an independent assignment queue.

### Example

Sector 48:
- Employee A.
- Employee B.
- Employee C.
- Employee D.

Assignment:

```text
Ticket 001 → Employee A
Ticket 002 → Employee B
Ticket 003 → Employee C
Ticket 004 → Employee D
Ticket 005 → Employee A
Ticket 006 → Employee B
```

### Assignment rules

1. Every newly submitted complaint enters the assignment engine.
2. The engine identifies the selected branch.
3. Fetch active employees from the dummy employee master.
4. Identify employees eligible for complaint assignment.
5. Assign the ticket to the next eligible employee.
6. Update the persistent branch assignment cursor.
7. Record the assignment in the database.
8. Send an assignment notification.
9. Repeat the cycle for the next complaint.

### Equal distribution rules

- Use FIFO round-robin.
- Each eligible employee receives an equal number of tickets over a complete assignment cycle.
- Maintain a separate cursor for each branch.
- Never mix assignment queues between branches.
- Assignment must be concurrency-safe.
- Maintain complete assignment history.
- Reopened complaints should retain their original assignee if still eligible.
- If the original assignee is unavailable, assign through the branch queue.

### Employee availability

An employee is eligible only if:
- Active in the employee master.
- Has the correct support role.
- Belongs to the relevant branch.
- Complaint assignment availability is enabled.

If unavailable, skip that employee.

Do not use workload-based distribution or weighted round-robin. The finalized requirement is equal distribution.

### No eligible employee

If no eligible employee is available:
- Create the complaint normally.
- Preserve NEW_COMPLAINT status.
- Put it into the unassigned queue.
- Notify branch manager and central support.
- Retry assignment when an eligible employee becomes available.

Implement assignment using PostgreSQL transactions and row-level locking.

# 10. CUSTOMER TICKET REOPENING

A customer must be able to reopen a resolved ticket using the same ticket ID.

### Reopening requirements

- Reopening is permitted only when the ticket is RESOLVED.
- The reopening deadline must not have expired.
- Verify the original registered mobile number.
- Require a reopening reason.
- Keep the original ticket ID.
- Do not create a duplicate complaint.
- Change the status to IN_PROGRESS.
- Record the reopening event.
- Preserve all previous status history.
- Notify the customer and assigned support employee.

### Reopening deadline

The reopening window must be configurable by Root Admin.

Do not hardcode 24, 48 or 72 hours.

Store the calculated `auto_close_at` timestamp on each ticket when it becomes RESOLVED.

Existing resolved tickets must retain their calculated deadlines when the global configuration changes, unless an authorized Root Admin explicitly applies a new policy.

### Reopening after closure

Once CLOSED, a ticket cannot be reopened by anyone.

Display:

"Your ticket has already been closed and can no longer be reopened. Please submit a new complaint if you need further assistance."

# 11. AUTOMATIC TICKET CLOSURE

Build a durable background closure engine.

When a ticket becomes RESOLVED:

1. Record resolution timestamp.
2. Fetch the active closure policy.
3. Calculate the reopening deadline.
4. Store the deadline in the ticket record.
5. Send customer resolution email.
6. Schedule automatic closure.

When the deadline expires:

1. Fetch the ticket.
2. Confirm that its status is still RESOLVED.
3. Confirm that the current time has reached its stored deadline.
4. Lock the ticket row.
5. Change the status to CLOSED.
6. Record status history.
7. Record audit event.
8. Send closure notification.
9. Mark the closure job completed.

The closure worker must be idempotent.

If the customer reopens the ticket before closure, cancel or invalidate the pending closure job.

Protect against simultaneous reopening and automatic closure using database transactions and row-level locking.

Do not rely on JavaScript timers or in-memory scheduling.

# 14. COMPLETE SECURITY REQUIREMENTS

Treat security as a core architectural requirement.

Implement security at the frontend, backend, API, database and infrastructure layers.

## A. Authentication security

- Use Supabase Auth for dummy development staff accounts.
- Use secure session handling.
- Verify JWT signatures, issuer, audience and expiry on the backend.
- Never trust frontend-supplied role or employee IDs.
- Implement secure password policies.
- Add login rate limiting.
- Add account lockout or progressive throttling after repeated failures.
- Support secure password reset.
- Provide logout and session revocation.
- Use MFA for Root Admin and privileged production accounts.
- Keep customer public access separate from employee authentication.

Production staff authentication should be integrated with FitClass CRM through a replaceable authentication adapter.

## B. Authorization security

Implement RBAC with resource-level checks.

Every protected request must validate:
- User identity.
- Tenant membership.
- Role.
- Permission.
- Branch access.
- Ticket ownership or assignment.
- Current ticket status.

Use deny-by-default authorization.

Do not depend on frontend visibility controls.

An employee must not access a ticket simply by changing the ticket ID in the API URL.

## C. PostgreSQL Row Level Security

Enable RLS on all sensitive tables.

Implement policies for:
- Complaint tickets.
- Ticket assignments.
- Ticket messages.
- Ticket attachments.
- Ticket history.
- Employee availability.
- Configuration records.
- Notification records.
- Audit logs.

Public anonymous users must not have direct database access to complaint records.

Use a secure backend service for public complaint submission and tracking.

Never expose the service-role key in frontend code.

The database must enforce tenant and branch restrictions wherever feasible.

## D. API security

Implement:
- HTTPS-only production traffic.
- Strict CORS allowlist.
- Request body size limits.
- Input validation.
- Output filtering.
- API rate limiting.
- Secure HTTP headers.
- SQL injection prevention.
- XSS prevention.
- CSRF protection where cookie-based sessions are used.
- Request timeouts.
- Secure error handling.
- API versioning.
- Idempotency keys.
- Abuse monitoring.

Never return stack traces, database errors, credentials or internal implementation details to clients.

## E. Customer tracking security

Ticket ID + mobile number must both match.

Additional controls:
- Normalize mobile numbers.
- Rate-limit failed tracking attempts.
- Use generic invalid-ticket responses.
- Apply progressive delays or temporary throttling.
- Avoid logging full phone numbers.
- Avoid placing phone numbers in URL query parameters.
- Return only minimum required customer data.
- Keep internal messages private.

Plan an optional OTP verification upgrade.

## F. File upload security

- Private storage buckets.
- Allowlisted MIME types.
- File signature verification.
- Maximum file size limits.
- Random server-generated filenames.
- Malware scanning before staff access.
- Short-lived signed URLs.
- No public attachment links.
- Prevent path traversal and malicious file uploads.

## G. Database and operational security

- Keep credentials in secret management.
- Separate development and production projects.
- Use least-privilege database roles.
- Encrypt communication.
- Maintain database backups.
- Implement audit logging.
- Protect closed tickets from modification.
- Apply database migration version control.
- Configure data retention.
- Avoid unnecessary sensitive data collection.
- Monitor unusual access and assignment patterns.

Never allow ordinary support agents to edit or delete audit history.
